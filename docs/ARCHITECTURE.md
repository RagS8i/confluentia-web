# Architecture

## Goals

- Turn messy multilingual source material into source-linked structured facts.
- Never let the language model decide a workflow status.
- Preserve every original claim and surface differences instead of resolving them.
- Fail safe: missing or unreliable data can never produce a reassuring routine status.
- Keep everything auditable and reversible (correction, override, deletion).

## Processing stages

| Stage | Module | Responsibility |
| --- | --- | --- |
| A | `pipeline/normalize.py` | Validate payloads, split segments, normalize text (NFKC, whitespace), assign stable source IDs, detect empty/low-confidence/unreadable/language warnings, detect prompt-injection text. |
| B | `pipeline/interpret.py` | Language readiness: declared vs heuristic language, ambiguity/uncertainty, unsupported language. |
| C | `pipeline/extract.py` | Per-source extraction via `BaseProvider`, bounded retries, exact-quote location, negation/uncertainty checks, per-fact source refs, no-source warnings. |
| D | `pipeline/timeline.py` | Parse temporal expressions, keep raw text, build an unvalidated timeline. |
| E | `pipeline/reconcile.py` | Group canonical facts, classify contradictions, historical-vs-current, unit mismatch, duplicate content, untraceable claims. |
| F | `triage/engine.py` | Deterministic rule evaluation, strict vs lenient matching, unresolved warnings, outcome aggregation, component warnings. |
| G | `pipeline/gaps.py`, `pipeline/summary.py`, `pipeline/urgency.py` | Missing-information gaps, multilingual questions, evidence-linked sections, validated draft note, and an advisory SLM urgency score computed after all available evidence is assembled. |
| - | `pipeline/orchestrator.py` | Stage state, persistence, component warnings, partial-failure handling, deletion/withdrawal race checks. |

Each stage records a `ProcessingRun` with attempt number and status. A failing stage is recorded; the pipeline continues where safe. Stage failures and per-source extraction failures make the case `partially_processed`; if no facts survive, it becomes `processing_failed` and `UNASSESSED`.

## Coordination services

The processing order is safety-sensitive:

1. Rules evaluate and warnings persist.
2. Emergency escalation is created and delivery is attempted immediately, before optional summaries, messages or follow-up work. A failure is recorded as stage failure `F1_urgent_escalation` and audit event `urgent_escalation_failed`.
3. Summary and gaps are generated.
4. Follow-up suggestions are synchronized from the persisted summary.

| Module | Responsibility |
| --- | --- |
| `communications.py` | Curated `en`/`hi`/`hinglish` templates, emergency blocking, draft/approve/send/dismiss, staff identity and audit. Patient-facing clinical messages cannot be sent without approval. |
| `followups.py` | Persistent summary-derived questions, staff approval, send/dismiss, answer capture with source attribution, and reprocessing. |
| `escalation.py` | Emergency escalation deduplication by case and trigger, outbox/webhook/failure delivery, retry and acknowledgement. Acknowledgement is operational receipt, not resolution. |
| `queue_ops.py` | Priority-category-preserving ranking with advisory urgency as the first within-category key, explainable factors, bottlenecks, explicit staffing state, and conservative wait estimates. |
| `outbound.py` | Delivery adapter shared by communications and escalations: `outbox`, opt-in `webhook`, or simulated `fail` for drills. |

Queue ranking never moves a case across priority categories and never auto-downgrades or reassigns. Within a category, a higher advisory urgency score is reviewed first, followed by the explainable operational score and arrival time. The urgency score is generated by the SLM after processing, can be edited by clinical staff with a recorded reason, and is preserved across reprocessing once edited. It is not a diagnosis, clearance or workflow outcome. Emergency cases receive no wait estimate. A wait estimate requires available clinicians, a recorded average review time and at least the configured observed sample; otherwise the API returns an unavailable estimate with a disclosure.

Communication and follow-up records remain linked to the case. Patient reads are limited to sent messages, sent/answered follow-ups and patient-authored answers. Staff views include drafts and delivery failures.

## Why the rule engine is separate

The SLM proposes candidate facts and a draft narrative. It is never trusted to set `EMERGENCY`/`PRIORITY_REVIEW`/`ROUTINE_REVIEW`. The rule engine:

- consumes only structured facts,
- re-validates type, label, status, unit, numeric thresholds, source traceability and confidence,
- emits reproducible warnings with rule IDs and evidence fact IDs,
- returns `UNASSESSED` when nothing evaluable exists, when a potential warning is unresolved, or when critical processing failed.

Lenient matching treats uncertain facts as *potential* matches so they route to humans; strict matching requires present status, a traceable source and sufficient confidence.

## Evidence links

Every fact carries `source_refs` with source ID, segment ID, character offsets and, where applicable, audio `start`/`end`, `page` and `bbox`. Facts with no locatable quote are marked `ai_suggestion` and `inferred_for_review`, produce a `no_source_reference` warning, and are excluded from the presenting complaint. Summaries expose `evidence_fact_ids` and coverage counts.

## Security and privacy

- `security.py` supports trusted development headers or API keys; role checks and per-case access checks run on every route.
- `storage.py` encrypts source text, fact payloads and uploads with Fernet. Keys come from `CAREFLOW_ENCRYPTION_KEY` or a generated dev key file.
- `db.py` stores only encrypted clinical content, including message bodies, follow-up text and answers; audit rows (actor, action, target, metadata) are plaintext and retained for accountability.
- Warning persistence merges by warning identity: later runs do not delete prior warnings, and acknowledged warnings remain acknowledged.
- `deletion.py` performs consent withdrawal/deletion as idempotent, resumable steps: mark withdrawn, delete sources, facts, derived data, communications, follow-ups, answers, escalations, documents, purge uploads, finalize.

## Concurrency and race handling

- One in-process lock per case prevents overlapping pipeline runs (`ProcessingConflict` -> HTTP 409).
- `Orchestrator._ensure_active` re-checks deletion and consent withdrawal before persisting facts and derived data, and before the final case save, so a run that races with a deletion job aborts instead of resurrecting content.
- Deletion jobs are safe to retry; completed steps are skipped.

## Statuses

Case status: `received`, `consent_pending`, `queued`, `processing`, `processed`, `partially_processed`, `processing_failed`, `reviewed`, `withdrawn`, `deleted`.

Workflow outcome: `EMERGENCY`, `PRIORITY_REVIEW`, `UNASSESSED`, `ROUTINE_REVIEW`. Overrides are recorded with the original status, new status, reviewer, role, timestamp and reason.

Communication status: `draft`, `approved`, `sent`, `failed`, `dismissed`. Follow-up status: `suggested`, `approved`, `sent`, `answered`, `dismissed`. Escalation status: `pending`, `sent`, `failed`, `acknowledged`.

Delivery modes are selected per service with `CAREFLOW_COMMUNICATION_DELIVERY` and `CAREFLOW_ESCALATION_DELIVERY`. The default `outbox` is auditable and local. `webhook` posts JSON to `CAREFLOW_OUTBOUND_WEBHOOK_URL`; `fail` exists for drills and tests. Delivery failure never clears the clinical warning or escalation, and retries are explicit.
